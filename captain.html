CP-1 Advanced JQL & flow metrics

60 minLive + labWorks in sandbox today

Objectives

  • Query history, not just the current state, using WAS and CHANGED with their predicates.
  • Use sprint, link and personal functions to answer planning questions in one query.
  • Turn JQL into four flow metrics: bounce-back rate, carry-over, aging WIP and blocked work.
  • Know where JQL stops and a reporting tool has to take over.

History operators: the time machine

Most people only query where work is. Captains also ask where work has been. Jira keeps a change history, and two operators read it:

OperatorAsksPredicates you can add
WAS / WAS NOT / WAS INDid this field ever have this value?BY, DURING, BEFORE, AFTER, ON
CHANGEDDid this field change, optionally from X to Y?FROM, TO, BY, DURING, BEFORE, AFTER, ON
The trap everyone hits

History operators only work on a few fields: Status, Assignee, Priority, Reporter, Resolution and Fix Version. You cannot run labels WAS Blocked or "Story Points" CHANGED. To track history on other fields, use automation to stamp a date field, or a reporting tool such as eazyBI that imports full change history (CP-3).

-- Every item that failed testing at least once
project = FLY AND status CHANGED FROM "eQE Testing" TO "Development"
ORDER BY priority DESC

Sandbox answer: FLY-19, FLY-21, FLY-25. FLY-25 bounced twice, but JQL can't count how many times. It's a yes/no filter, and counting is a job for eazyBI.

project = FLY
AND status CHANGED FROM "eQE Testing" TO "Development" AFTER -14d
-- add: BY "account-id-or-name" to scope to one tester
ORDER BY updated DESC
project = FLY AND status WAS "eQE Testing" DURING (startOfDay(-14d), now())

Sprint, link and personal functions

project = FLY AND sprint in closedSprints() AND sprint in openSprints()

Sandbox answer: FLY-20, the rest-rule warning story that slipped out of JET-2026.q4.2.

issue in linkedIssues("FLY-24", "blocks")
project = FLY AND statusCategory != Done
AND issueLinkType = "is blocked by"
issue in issueHistory() ORDER BY lastViewed DESC
project = FLY AND sprint in futureSprints()
AND status not in ("Ready", "To Do")

Four flow metrics you can pull from JQL today

Bounce-back rate

Share of items that failed eQE at least once.

count(CHANGED FROM "eQE Testing" TO "Development") ÷ count(status WAS "eQE Testing")

Carry-over

Work that didn't finish in the sprint it was planned for.

sprint in closedSprints() AND sprint in openSprints()

Aging WIP

In progress but untouched for 5+ days. Looks like it's moving, but it isn't.

statusCategory = "In Progress" AND NOT status CHANGED AFTER -5d

Blocked now

Flagged or labeled blocked. (Use automation to measure how long work stays blocked; see CP-5.)

Flagged is not EMPTY OR labels = Blocked
project = FLY AND sprint in openSprints()
AND statusCategory = "In Progress"
AND NOT status CHANGED AFTER -5d
ORDER BY updated ASC
Make it a habit

Save each metric query as a filter named with the team code (e.g. JET · Bounce-backs 14d) and put them on a dashboard with the Filter Results and Two Dimensional Filter Statistics gadgets. You'll build exactly this in CP-M1. For 20 graded challenges, fly the JQL Simulator.

CP-2 Plans & capacity planning

60 minInstructor demo + labRequires Jira Premium

Objectives

  • Build a plan from the boards and projects a program actually uses.
  • Set team capacity per sprint and spot overload before it happens.
  • Use scenarios to test "what if" without touching real work items.
  • Map and resolve cross-team dependencies, then commit changes back to Jira on purpose.
Premium only

Plans is part of Jira Premium and Enterprise. To run this module hands-on, United needs a Premium training site (or a Premium trial on the sandbox) with the FLY project imported. Without it, CP-2 runs as an instructor demo.

The pre-flight: build the plan

  1. Create a plan from the Plans menu. Choose sources: boards (best, because sprints come along), projects, or saved filters. For FLY, add the Jetstream - Sprint Board.
  2. Set hierarchy and scope: Epic → Story/Task/Bug/Spike. Exclude Done older than 30 days to keep it fast.
  3. Add teams: map each source board to a team. Plans can use shared Atlassian teams, which line up with the Team field the standards deck recommends.
  4. Configure capacity: for Scrum teams, set capacity in story points per sprint. Start with the trailing three-sprint average from the Velocity report, not a hopeful number.
  5. Pick a scheduling mode: story points with sprints for Scrum teams; days or hours for Kanban teams.

Fly the plan

FeatureWhat it answersCaptain's move
Timeline + capacity barsWhich sprint is over-committed?Red capacity bars mean move work or cut scope. Don't ignore them.
ScenariosWhat if we lose 30% of a team for holiday cover?Duplicate the baseline, change capacity in the scenario only, compare.
Dependencies viewWhat crosses team or sprint boundaries?Fix any dependency scheduled after the work that needs it.
Auto-scheduleWhat's the fastest feasible order?Preview first, accept selectively. Never accept blind.
ReleasesWill Mobile 5.3 land on 15 Dec?Compare the release date to the projected finish of its work.
Review changesWhat will I actually write back to Jira?Changes in Plans stay in the plan until you Save to Jira. Review every row.

How this connects to the Golden Template

The standard asks teams to keep 2–3 sprints of Ready work on the Backlog Readiness board. Plans turns that from a gut feeling into a number:

project = FLY AND status = "Ready" AND issuetype in (Story, Task, Bug, Spike)

Sum the story points (use the Story Points column sum in the list view, or the plan's roll-up). If the Ready total is below 2× team capacity, refinement is the bottleneck, not delivery.

CP-3 Reporting with eazyBI

60 minInstructor demo + spec labRequires eazyBI app

Objectives

  • Import Jira data into eazyBI with the right custom fields and change history.
  • Read a report as measures × dimensions × filters.
  • Build velocity, cycle time, bounce-back and created-vs-resolved reports, and share them on a dashboard.
Prerequisite

eazyBI for Jira is a Marketplace app. It's not installed in the sandbox yet. Ask the Jira admins to install it on the training site, and to grant attendees a role that can create reports in a training account.

The mental model

Measures (the numbers)

Counts and sums: issues created, issues resolved, story points resolved, and with history imported, transition counts and days in status.

Dimensions (the slices)

Time, Project, Issue Type, Status, Sprint, Fix Version, Label, Assignee, Transition and Transition Status. Put one on rows, one on columns, and filter with pages.

Import settings that make or break your reports

Four reports every DT team should have

ReportRows × columnsWhy it beats the built-in chart
Velocity, committed vs completedSprint × sprint story-point measuresCross-team and cross-project on one chart; filter by component.
Cycle time by typeTime (weeks) × average days from Development to Done, split by Issue TypeSeparates bug flow from story flow, which the Control Chart blends.
eQE bounce-back rateSprint × (transitions eQE Testing → Development ÷ items entering eQE Testing)Counts every bounce, including FLY-25's two. JQL can't do that.
Created vs resolvedTime (weeks) × issues created, issues resolvedShows whether the backlog grows faster than the team can absorb.
CASE WHEN ([Measures].[Transitions to status], [Transition Status].[eQE Testing]) > 0
THEN
  ([Measures].[Transitions from status], [Transition].[eQE Testing => Development])
  /
  ([Measures].[Transitions to status], [Transition Status].[eQE Testing])
END
From the flight deck

Measure names and the transition member format vary by eazyBI version and import settings. Treat the MDX as a pattern: find the real member names in the dimension picker, then adapt. Format the result as a percentage.

CP-4 Zephyr at scale: traceability & release gates

45 minInstructor demo + design labRequires Zephyr app

Objectives

  • Trace any requirement through test case, execution and defect, in both directions.
  • Read coverage per epic and per release.
  • Define a release-readiness gate that fits the Golden Template's Ready for Release state.
Know your edition

SmartBear sells more than one Zephyr product for Jira Cloud, and they model tests differently. One keeps test cases, cycles and plans as its own objects inside Jira; the other makes a "Test" a Jira work type. Confirm which edition United licenses before class. Screens and terms in this lesson follow the first model.

The traceability chain

Story FLY-21→ Test cases (coverage)→ Test cycle: Mobile 5.3 regression→ Executions: Pass / Fail / Blocked→ Bug FLY-25 (from failed step)

When eQE fails a story, they log the defect from the failed execution, so the bug links to the test and the story automatically. That's the difference between "we found a bug" and "we can prove which requirement is at risk".

Coverage questions to ask before every release

  • Which stories in Mobile 5.3 have no linked test case?
  • Which linked test cases have no execution in the current cycle?
  • Which executions failed, and does each failure have a linked Bug?
  • Are any linked Bugs still open at High or Highest priority?
project = FLY AND fixVersion = "Mobile 5.3"
AND type = Bug AND statusCategory != Done
AND priority in (Highest, High)
Where this fits the template

The exit criteria for Ready for Release say testing is complete, the PO has approved, and every acceptance criterion is met. Zephyr provides the evidence for "testing complete": 100% of linked tests executed in the release cycle, zero failed without a linked defect, and zero open Highest or High bugs.

CP-5 Automation & Rovo agents

45 minLive + design labAutomation works in sandbox

Objectives

  • Design rules as Trigger → Condition → Action with smart values.
  • Automate the Golden Template's housekeeping so humans don't have to remember it.
  • Decide when a Rovo agent belongs in the loop, and how to govern and audit it.

Anatomy of a rule

When Trigger: field value changed, work item transitioned, scheduled (with JQL), manual, incoming webhook…
If Conditions: JQL condition, field condition, "related work items" condition…
Then Actions: edit field, transition, comment, send message, create work item, branch to parent or sub-tasks…

Smart values put live data into actions, e.g. {{issue.key}}, {{issue.summary}}, {{issue.status.name}}, {{issue.assignee.displayName}}, {{issue.url}}, {{now}}.

Three rules that enforce the template

RuleTriggerConditionAction
Blocked means flaggedField value changed: LabelsLabels contains BlockedSet Flagged = Impediment; comment "Blocked at {{now}}"
Parent follows childrenWork item transitioned to DoneAll sibling items are DoneBranch to parent epic → transition to Done (or comment for PO review)
Aging alertScheduled, daily 08:00JQL: sprint in openSprints() AND statusCategory = "In Progress" AND NOT status CHANGED AFTER -5dComment mentioning the assignee + message to the team channel
Test like a pilot

Build rules in the sandbox first, scope them to one project, and read the audit log after every test run. A rule that loops (for example, an edit that triggers itself) can burn through your automation limit in minutes. Leave "allow other rules to trigger this rule" off unless you really need it.

Rovo agents in the workflow

Agents in Jira (generally available since Team '26) let teams assign work items to Rovo or third-party agents, work with them in comments, and trigger them from automation rules or board columns. Every agent action is logged.

Good agent jobs

  • Draft acceptance criteria when an item enters Team Refinement
  • Check a story against the Definition of Ready before it moves to Ready
  • Summarize a long eQE comment thread into a fix checklist
  • Draft release notes from the Ready for Release column

Keep a human in the seat

  • Closing or transitioning work that feeds velocity
  • Changing estimates, sprint scope or fix versions
  • Anything customer-facing
  • Anything that acts on text from outside the org (see FLY-55 in MCP-M6)
Governance

Admins can separate using AI from building agents. Only a small group builds agents today, with a submission process planned. Automations and agents built in Rovo Studio inherit the builder's permissions, and Studio-built agents consume Rovo credits per use. Name an owner for every agent, document its purpose and scope, and review its audit trail regularly.

CP-7 Jira ↔ Git

30 minLive demoNeeds a connected demo repo

Objectives

  • Connect a Git host so branches, commits, PRs, builds and deployments show on work items.
  • Use issue keys consistently so the links happen on their own.
  • Use smart commits safely, and query development data with JQL.

Connect

Install the Atlassian-provided integration for your host (GitHub, GitLab or Bitbucket), connect the organization, and choose the repositories. After the backfill, the work item's Development panel shows branches, commits, pull requests, builds and deployments.

The one rule: put the key everywhere

WhereExample
Branchfeature/FLY-21-gate-change-push
CommitFLY-21 Dedupe alerts by event sequence number
Pull request titleFLY-21: Gate change push notification (iOS + Android)

Smart commits

git commit -m "FLY-21 #comment Cache fix for Android 15 double-gate bug #time 1h 30m #ready-for-eqe"
Read before you fly
  • An admin must enable smart commits for the integration, and the committer's email must match a Jira user.
  • The transition command matches a transition name, with spaces written as hyphens. If the name is ambiguous or not allowed from the current status, nothing happens.
  • Smart-commit transitions move work as you and feed cycle time. Don't let them skip eQE or PO Review.
project = FLY AND development[pullrequests].open > 0
project = FLY AND statusCategory = Done AND issuetype in (Story, Bug)
AND development[commits].all = 0 AND resolved >= -30d

These development fields return nothing until a repo is connected to the site.

MISSION CP-M5

Automation: "Blocked > 2 days escalates"

Turbulence
Mission brief FLY-22 is blocked by FLY-24. Nobody noticed for days. JQL can't see label history, so design an automation pair that measures blocked time and escalates after 2 days, then build it in the sandbox.

Capstone

IROPS Day

A winter storm grounds the hub. In 60 minutes your crew triages, re-plans, reports and communicates using everything from Levels 1–3, including Rovo and a Claude co-pilot under the Co-Pilot Protocol.

Start the capstone →

Captain checkride

Ten questions. Pass with 80% to earn your fourth stripe.

1. Which query finds items that failed eQE at least once?

CHANGED FROM … TO … reads the transition history. The first option only finds items currently in Development. The third fails: label history isn't searchable.

2. Why can't JQL tell you that FLY-25 bounced twice?

JQL returns a set of work items. Counting transitions needs imported change history in a reporting tool.

3. Which fields support the WAS and CHANGED operators?

History search works on a fixed set of system fields. For anything else, stamp dates with automation or use eazyBI.

4. In Plans, what does a scenario let you do?

Changes in a plan stay in the plan until you review and save them to Jira. Scenarios let you compare options side by side.

5. The Golden Template asks for 2–3 sprints of Ready work. With capacity of 30 points per sprint, what's the minimum Ready runway?

2 sprints × 30 points = 60 points of Ready work at minimum, and 90 at the top of the range.

6. Which eazyBI import setting is required for bounce-back and time-in-status reports?

Transitions and time-in-status come from change history. Without it, you only see current values.

7. An eQE tester finds a failure while executing a Zephyr test. What's the best way to log the bug?

Logging from the execution keeps traceability intact. The standards also say to standardize on the Bug type, not a "defect" label. See FLY-44 for the anti-pattern.

8. Your scheduled automation rule edits a field, and another rule triggers on that field. What's the risk?

Rules can trigger other rules if you allow it. Keep that option off unless you need it, and check the audit log after every test.

9. What's true about automations built in Rovo Studio?

Studio-built automations inherit the builder's permissions. Another reason to name an owner for each one and review it.

10. A smart commit FLY-21 #ready-for-eqe doesn't move the item. What's the most likely cause?

Smart commits need to be enabled, a matching user, and a valid transition name for the current status. Branch names help linking, but they don't drive commands.
